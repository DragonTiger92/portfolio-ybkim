# Functional Requirements

This document is the single source of truth for user-facing behavior.

## FR-001: First-Viewport Positioning

| Field    | Value         |
| -------- | ------------- |
| Status   | Draft         |
| Priority | P1            |
| Phase    | `PH-002`      |
| Source   | Project Brief |

The first viewport must clearly present YB Kim as a frontend-specialized
full-stack web developer.

### FR-001 Acceptance Criteria

- The headline or primary copy communicates frontend strength and full-stack
  delivery breadth.
- Current job-seeking status is easy to understand without scrolling deeply.
- The first viewport includes a clear next action such as project review,
  resume/contact access, or repository inspection.

## FR-002: Public-Safe Project Summaries

| Field    | Value    |
| -------- | -------- |
| Status   | Draft    |
| Priority | P1       |
| Phase    | `PH-002` |
| Source   | Content  |

The site must summarize representative public projects without using private or
applicant-only work as public source material.

### FR-002 Acceptance Criteria

- Each project summary states the problem, role, stack category, and outcome.
- Applicant-only or private work evidence is excluded from public case-study
  source docs unless it receives a fresh disclosure review.
- Project summaries remain short enough to scan in a recruiting context.

## FR-003: Repository And Contact Navigation

| Field    | Value    |
| -------- | -------- |
| Status   | Draft    |
| Priority | P1       |
| Phase    | `PH-003` |
| Source   | Product  |

Visitors must be able to access the public GitHub repository and contact paths.

### FR-003 Acceptance Criteria

- Repository access is visible from persistent or repeated navigation.
- Contact actions use public-safe channels only.
- Labels make the destination and purpose clear.

## FR-004: Skills And Work Style Evidence

| Field    | Value    |
| -------- | -------- |
| Status   | Draft    |
| Priority | P1       |
| Phase    | `PH-003` |
| Source   | Content  |

The site must connect skills to evidence rather than listing tools without
context.

### FR-004 Acceptance Criteria

- Frontend, integration, deployment, documentation, and verification skills are
  grouped by role in delivery.
- At least one project or work example supports each major skill group.
- Tool names do not dominate the copy at the expense of responsibility and
  problem-solving context.
